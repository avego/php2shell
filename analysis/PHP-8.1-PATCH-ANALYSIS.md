# Полный сравнительный анализ патчей безопасности PHP 8.1.34 и 8.1.29

**Дата аудита:** Ноябрь 2026 г.  
**Целевые версии:** PHP 8.1.34 (финальный EOL-релиз ветки 8.1) и PHP 8.1.29 (базовый релиз дистрибутивов)  
**Эталон сравнения:** Upstream PHP 8.2.35 (официальный релиз с закрытием уязвимостей)  
**Анализируемые патчи:**
* `php-8.1.34-cve-2026-109618-109619.patch` (344 949 байт, 9 506 строк)
* `php-8.1.29-cve-2026-109618-109619.patch` (344 528 байт, 9 496 строк)  
**Происхождение патча:** Бэкпорт коммита `1e06d14c` (Remi Collet, `remicollet/php-src-security`) на базе архитектуры Арно Ле Блана (`01a40e89fb`, PHP 8.2+).

---

## 1. Анатомия уязвимостей (CVE-2026-109618 и CVE-2026-109619)

### Механика проблемы в непатченном PHP:
1. **Жесткий Bailout при исчерпании памяти:**
   В оригинальном коде PHP при превышении `memory_limit` аллокатор Zend MM (`emalloc`, `safe_emalloc`, `erealloc`) не возвращает `NULL`. Вместо этого он немедленно вызывает:
   ```c
   zend_error_noreturn(E_ERROR, "Allowed memory size of %zu bytes exhausted...");
   ```
   Функция `zend_error_noreturn` выполняет `zend_bailout()`, который совершает нелокальный переход `longjmp()` на верхний уровень цикла обработки запроса (`zend_try`).

2. **Повреждение внутреннего состояния (State Corruption):**
   Если OOM случается в момент разбора сетевых данных (например, парсер `multipart/form-data` в `main/rfc1867.c`), `longjmp` мгновенно прерывает выполнение посреди заполнения связанных списков (`zend_llist`), выделения памяти под MIME-заголовки или добавления элементов в хэш-таблицу `SG(rfc1867_uploaded_files)`.
   В результате:
   * Локальные буферы не освобождаются.
   * Указатели в глобальных структурах остаются смотреть на наполовину инициализированную память или содержат неочищенные адреса.

3. **Фаза Use-After-Free (UAF) и RCE (php2shell):**
   После перехвата `longjmp` ядро PHP переходит к фазе завершения запроса (`php_request_shutdown`). Во время выполнения деструкторов ядра вызываются очистки зарегистрированных структур:
   * `destroy_uploaded_files_hash()`
   * Деструкторы списков заголовков (`zend_llist_destroy`)
   * Обработчики суперглобальных массивов `$_POST` и `$_FILES`
   Поскольку структуры повреждены, деструктор обращается к уже освобождённой или контролируемой атакующим памяти, что приводит к перезаписи таблиц функций (vtable / function pointers) и выполнению произвольного кода.

## 2. Архитектура эталонного исправления в PHP 8.2.35

В upstream PHP 8.2.35 (коммит Арно Ле Блана `01a40e89fb`) проблема решена не косметической правкой парсера, а **фундаментальной переработкой архитектуры управления памятью ядра Zend Engine**:

### Ключевые компоненты upstream-архитектуры:
1. **Двухуровневый лимит памяти (Soft Limit vs Hard Limit):**
   * **Soft Limit (`heap->limit`)** — штатный `memory_limit` (например, 128 МБ).
   * **Hard Limit (`heap->hard_limit`)** — жесткий потолок, по умолчанию составляющий **125%** от Soft Limit (регулируется новой INI-директивой `memory_hard_limit_percent`).

2. **Концепция Soft-OOM (Отложенный отказ):**
   * При превышении `heap->limit` аллокация **НЕ падает** и `longjmp` **НЕ вызывается**!
   * Память выделяется из подушки безопасности (headroom 25%).
   * Устанавливается флаг отложенной ошибки:
     ```c
     EG(delayed_oom).state = ZEND_OOM_STATE_PENDING;
     zend_atomic_bool_store_ex(&EG(vm_interrupt), true);
     ```
   * Функция, выполнявшая разбор (например, `rfc1867_post_handler`), продолжает выполнение, корректно закрывает все открытые узлы, очищает временные структуры и штатно возвращает код ошибки через `return`.

3. **Безопасная точка выгрузки (Safe Bailout Boundary):**
   * Ошибка OOM выбрасывается только тогда, когда поток управления доходит до безопасной границы:
     * В SAPI — сразу после завершения вызова обработчика тела в `sapi_handle_post()`:
       ```c
       if (ZEND_HAS_OOM()) {
           zend_handle_delayed_oom();
       }
       ```
     * В виртуальной машине Zend VM — на границе между опкодами через прерывание `ZEND_VM_INTERRUPT()`.
   * Функция `zend_handle_delayed_oom()` выбрасывает фатал уже в **чистом, непротиворечивом состоянии ядра**, где все списки закрыты, а глобальные указатели обнулены.

4. **Аварийный предохранитель (Hard Panic):**
   * Если эксплойт атакующего пытается непрерывно аллоцировать память и съедает весь 25%-й запас Hard Limit, срабатывает аварийная защита:
     ```c
     zend_mm_delayed_error_or_panic(..., _exit(1));
     ```
     Происходит мгновенный системный вызов ядра ОС `_exit(1)`. Никакой код завершения PHP, деструкторы или перехватчики `register_shutdown_function` не вызываются, исключая возможность эксплуатации UAF.

## 3. Детальный аудит бэкпорта для PHP 8.1.34 и 8.1.29

### 3.1. Масштаб изменений
Бэкпорт затрагивает **104 исходных файла**:
* **Zend Engine (25 файлов):** аллокатор памяти, диспетчер виртуальной машины, строковые фабрики `smart_str`, хэш-таблицы, исключения.
* **Core & SAPI (7 файлов):** `main/SAPI.c`, `main/rfc1867.c`, `main/main.c`, `main/php_variables.c`, потоковая память.
* **Расширения (71 файл):** `mbstring`, `json`, `standard`, `session`, `opcache`, `soap`, `xml`, `gd`, `date`, `filter` и др.
* **SAPI (1 файл):** `sapi/phpdbg/phpdbg.c`.

### 3.2. Проверка наложения (Patch Hygiene)
* **PHP 8.1.34:** Патч накладывается **100% чисто** (`0 FAILED`, 0 `.rej`, 0 смещений).
* **PHP 8.1.29:** Патч накладывается **100% чисто** (`0 FAILED`, 0 `.rej`). Смещения в строках (offsets от -1 до -24 строк) вызваны штатным развитием кода между 8.1.29 и 8.1.34 и успешно разрешены утилитой `patch`.

### 3.3. Разбор ключевых подсистем

#### А. Ядро аллокатора (`Zend/zend_alloc.c` и `Zend/zend_alloc.h`)
* В структуры данных `zend_mm_heap` внедрены поля:
  * `size_t hard_limit;`
  * `zend_long hard_limit_percent;`
* Добавлен макрос быстрого определения состояния мягкого OOM:
  ```c
  #define ZEND_HAS_OOM() (EG(delayed_oom).state != ZEND_OOM_STATE_NONE)
  ```
* Реализована функция регистрации директивы:
  ```c
  ZEND_API zend_result zend_set_memory_hard_limit_percent(zend_long percent);
  ```
* Добавлен обработчик прерывания `zend_handle_delayed_oom()`, выбрасывающий исключение или вызывающий безопасный `zend_error_zstr_at()`.

#### Б. Защита парсера RFC 1867 (`main/rfc1867.c`)
В файле `main/rfc1867.c` бэкпорт внедряет комплексную защиту от сетевых атак:
1. **Фильтрация и дедупликация MIME-заголовков:**
   ```c
   static bool php_mime_should_save_hdr(const char *name)
   {
       return !strcasecmp(name, "Content-Disposition")
           || !strcasecmp(name, "Content-Type");
   }
   ```
   Парсер отбрасывает любые мусорные заголовки, предотвращая исчерпание памяти гигантскими заголовками в multipart-частях.
2. **Проверка превышения `post_max_size` в буфере:**
   ```c
   if (SG(post_max_size) > 0 && SG(read_post_bytes) > SG(post_max_size)) {
       return 0;
   }
   ```
3. **Безопасная обработка Soft-OOM в цикле парсинга:**
   ```c
   if (ZEND_HAS_OOM()) {
       goto oom;
   }
   ...
   oom:
       if (key) {
           efree(key);
       }
       smart_string_free(&buf_value);
       return 0;
   ```
   При нехватке памяти парсер аккуратно освобождает локальные структуры и возвращает код ошибки, не вызывая аварийного `longjmp`.
4. **Обнуление глобальных указателей при очистке:**
   ```c
   zend_hash_destroy(SG(rfc1867_uploaded_files));
   FREE_HASHTABLE(SG(rfc1867_uploaded_files));
   SG(rfc1867_uploaded_files) = NULL;
   ```
   Исключает Use-After-Free при повторных вызовах очистки в процессе shutdown.

#### В. Связанные списки (`Zend/zend_llist.c`)
В ветке PHP 8.1 функция `zend_llist_destroy` уже содержит сброс указателей:
```c
l->head  = NULL;
l->tail  = NULL;
l->count = 0;
```
Это предотвращает повисшие указатели в списках ядра при любых сценариях сбоя.

#### Г. Диспетчер виртуальной машины (`Zend/zend_vm_def.h` / `zend_vm_execute.h`)
* В макрос проверки системных прерываний `ZEND_VM_INTERRUPT()` добавлена проверка `ZEND_HAS_OOM()`.
* При обнаружении взведённого флага виртуальная машина плавно передаёт управление в `zend_handle_delayed_oom()`, сохраняя целостность стека вызовов и локальных переменных фрейма.

## 5. Оценка устойчивости против векторов атак

1. **Атака вложенными ключами массивов (`a[][a][a]...`):**
   * *Поведение:* Создает миллионы промежуточных хэш-таблиц.
   * *Результат с патчем:* При достижении `memory_limit` срабатывает Soft-OOM. Добавление элементов корректно прекращается по `!ZEND_HAS_OOM()`. Управление возвращается в `sapi_handle_post`, где вызывается чистый фатал. В памяти не остаётся циклических ссылок или повреждённых бакетов. **Успешно нейтрализована.**

2. **Атака исчерпанием жесткого лимита (Hard Limit Exhaustion):**
   * *Поведение:* Запрос пытается одномоментно выделить буфер, превышающий 25%-й запас подушки безопасности.
   * *Результат с патчем:* Срабатывает ветка `zend_mm_delayed_error_or_panic`, которая вызывает прямой вызов `_exit(1)`. Процесс мгновенно завершается операционной системой. Эксплуатация UAF на этапе `php_request_shutdown` физически невозможна. **Успешно нейтрализована.**

3. **Спуфинг деструкторов и Double Free:**
   * *Поведение:* Вызов деструкторов наполовину заполненных списков или уничтожение `SG(rfc1867_uploaded_files)`.
   * *Результат с патчем:* Все глобальные и локальные указатели явно обнуляются (`NULL`). Повторные вызовы деструкторов безопасны (`no-op`). **Успешно нейтрализована.**
