# Полный технический анализ патча безопасности PHP 5.5.38

**Дата разработки и аудита:** Ноябрь 2026 г.  
**Целевая версия:** PHP 5.5.38 (финальный релиз ветки PHP 5.5, Zend Engine 2.5)  
**Эталон сравнения:** Upstream PHP 8.2.35 и проверенные бэкпорты PHP 5.4.45 / PHP 5.6.40  
**Сформированный патч:** `php-5.5.38-cve-2026-109618-109619.patch` (35 308 байт, 1 088 строк)  
**Базовая архитектура:** Двухуровневый Soft-OOM аллокатор Арно Ле Блана, адаптированный под архитектуру Zend Engine 2.5.

---

## 1. Архитектурное положение PHP 5.5 (Zend Engine 2.5)

PHP 5.5 занимает промежуточное положение между PHP 5.4 и PHP 5.6:
1. **Сходство с PHP 5.6:**
   * В PHP 5.5 впервые появились генераторы (`yield`), блок `finally`, расширение OPcache в ядре и функция `password_hash()`.
   * Структура файлов диспетчера опкодов `Zend/zend_vm_execute.h` и `zend_vm_execute.skl` уже соответствует стандарту 5.6.
2. **Сходство с PHP 5.4:**
   * Сканер десериализатора `ext/standard/var_unserializer.c` сгенерирован компилятором `re2c 0.13.7.5`.
   * Потоковая модель и таблицы конфигурации INI (`main/main.c`) имеют схожее позиционирование макросов.
3. **Устраняемые дефекты безопасности:**
   * Жесткий аварийный прыжок `longjmp` (`zend_bailout`) при исчерпании `memory_limit`, приводящий к разбору поврежденных структур.
   * Отсутствие сброса указателей `l->head` и `l->tail` в `zend_llist_destroy()`.
   * Отсутствие фильтрации сторонних заголовков multipart/form-data и проверки переполнения буфера в `rfc1867.c`.

## 3. Детальный аудит защитных механизмов

### 3.1. Устранение Use-After-Free в связанных списках (`Zend/zend_llist.c`)

В оригинальном `php-5.5.38`:
```c
// До патча:
ZEND_API void zend_llist_destroy(zend_llist *l)
{
    zend_llist_element *current=l->head, *next;
    while (current) {
        next = current->next;
        if (l->dtor) l->dtor(current->data);
        pefree(current, l->persistent);
        current = next;
    }
    l->count = 0; // l->head и l->tail оставались висячими указателями!
}
```

Патч вносит исправление:
```diff
--- a/Zend/zend_llist.c
+++ b/Zend/zend_llist.c
@@ -109,6 +109,8 @@
 		current = next;
 	}
 
+	l->head  = NULL;
+	l->tail  = NULL;
 	l->count = 0;
 }
```
**Эффект безопасности:** Полная блокировка возможности повторного освобождения узлов или обращения по висячему адресу памяти при выходе из прерванного парсинга.

### 3.2. Архитектура Soft-OOM и Hard Limit (`Zend/zend_alloc.c` и `zend_alloc.h`)

1. **Динамический расчет Hard Limit (`zend_mm_update_hard_limit`):**
   ```c
   size_t headroom = MIN(heap->limit, (size_t) 1024 * 1024 * 1024);
   size_t hard_limit = (heap->limit > (size_t) -1 - headroom) ? (size_t) -1 : heap->limit + headroom;
   heap->hard_limit = hard_limit;
   ```
   Аллокатор выделяет безопасный коридор (headroom) сверх мягкого лимита `memory_limit` (до +100% объема, но не более 1 ГБ).
2. **Мягкое состояние ошибки OOM (`EG(delayed_oom)`):**
   * При достижении значения `limit` выставляется флаг:  
     `EG(delayed_oom) = ZEND_OOM_STATE_PENDING;`
   * Аллокатор **не прерывает** поток исполнения, позволяя парсеру POST штатно завершить разбор и очистить ресурсы.
3. **Безопасная точка аварийной паники (`_exit(137)`):**
   * Если приложение пытается потребить больше жесткого предела (`heap->hard_limit`), срабатывает функция `zend_mm_hard_limit_error`:
     ```c
     fprintf(stderr, "Hard memory limit of %lu bytes exhausted (tried to allocate %lu bytes)...\n", ...);
     _exit(137);
     ```
   * Код завершения `137` (SIGKILL) мгновенно убивает процесс ОС без вызова деструкторов PHP, полностью исключая эксплуатацию состояния гонки или повреждения памяти.

---

### 3.3. Защита сетевого парсера RFC 1867 (`main/rfc1867.c`)

1. **Строгая фильтрация MIME-заголовков:**
   ```c
   static zend_bool php_mime_should_save_hdr(const char *name)
   {
       return !strcasecmp(name, "Content-Disposition")
           || !strcasecmp(name, "Content-Type");
   }
   ```
   Парсер сохраняет только критически необходимые заголовки. Любые пользовательские или мусорные заголовки отбрасываются до аллокации.
2. **Отсечение по `post_max_size` в буфере:**
   ```c
   if (SG(post_max_size) > 0 && SG(read_post_bytes) > SG(post_max_size)) {
       return 0;
   }
   ```
   Блокирует переполнение буфера входящими сетевыми пакетами.
3. **Безопасный выход по `goto oom`:**
   В случае нехватки памяти парсер очищает выделенные ресурсы и возвращает `0`, не повреждая глобальное состояние ядра.
