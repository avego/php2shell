## 1. Специфика ветки PHP 8.0

PHP 8.0 является первым мажорным релизом на движке **Zend Engine 4**:
1. **Первое поколение JIT (Just-In-Time Compiler):** В 8.0 JIT поддерживал только архитектуру `x86/x86_64` (поддержка ARM64 появилась позже в 8.1). При возникновении OOM JIT-код также обязан проверять состояние прерываний аллокатора.
2. **Уязвимость `zend_llist_destroy`:** В оригинальном релизе PHP 8.0.30 функция `zend_llist_destroy` сбрасывала только `count = 0`, оставляя `head` и `tail` смотреть на уже освобождённые блоки памяти (`pefree`).
3. **CLI Web Server (`sapi/cli`):** В режиме встроенного сервера при сбое на этапе startup состояние аллокатора могло протекать в следующий запрос.

## 3. Детальный аудит ключевых компонентов защиты

### 3.1. Устранение Use-After-Free в связанных списках (`Zend/zend_llist.c`)

В оригинальном `php-8.0.30/Zend/zend_llist.c`:
```c
// УЯЗВИМЫЙ КОД ДО ПАТЧА:
ZEND_API void zend_llist_destroy(zend_llist *l)
{
    zend_llist_element *current=l->head, *next;
    while (current) {
        next = current->next;
        if (l->dtor) l->dtor(current->data);
        pefree(current, l->persistent);
        current = next;
    }
    l->count = 0; // ОШИБКА: l->head и l->tail НЕ ОБНУЛЯЛИСЬ!
}
```

Патч вносит критическое исправление:
```diff
--- a/Zend/zend_llist.c
+++ b/Zend/zend_llist.c
@@ -112,6 +112,8 @@
 		current = next;
 	}
 
+	l->head  = NULL;
+	l->tail  = NULL;
 	l->count = 0;
 }
```
**Эффект безопасности:** При двойном уничтожении списка или вызове деструктора после прерванного парсинга `l->head` гарантированно равен `NULL`. Цикл очистки превращается в `no-op`, предотвращая эксплуатацию UAF.

### 3.2. Двухуровневый аллокатор Soft-OOM (`Zend/zend_alloc.c` и `zend_alloc.h`)

В ядро аллокатора памяти Zend MM интегрирован полноценный механизм отложенного выхода:
* Добавлена структура `zend_oom_info` в `EG(delayed_oom)`:
  * `state`: состояние (`ZEND_OOM_STATE_NONE`, `PENDING`, `HANDLING`).
  * `message`: сообщение об ошибке, аллоцированное персистентно, чтобы не зависеть от исчерпанного пула запроса.
* Введены две границы:
  * **Soft Limit (`limit`)** — значение директивы `memory_limit`.
  * **Hard Limit (`hard_limit`)** — значение по умолчанию 125% от Soft Limit (`memory_hard_limit_percent`).
* При пересечении Soft Limit:
  ```c
  EG(delayed_oom).state = ZEND_OOM_STATE_PENDING;
  zend_atomic_bool_store_ex(&EG(vm_interrupt), true);
  ```
  Память продолжает выделяться из резервной 25%-й подушки, предотвращая панику ядра в момент незавершённых C-операций.
* При пересечении Hard Limit:
  ```c
  zend_mm_delayed_error_or_panic(..., _exit(1));
  ```
  Мгновенный системный вызов ядра ОС `_exit(1)` пресекает любую возможность захвата управления через цепочки вызовов деструкторов.

### 3.3. Защита сетевого парсера RFC 1867 (`main/rfc1867.c`)

Бэкпорт полностью синхронизирует логику `rfc1867.c` с эталонным PHP 8.2:
1. **Фильтрация MIME-заголовков (`php_mime_should_save_hdr`):**
   Разрешены только `Content-Disposition` и `Content-Type`. Все остальные заголовки парсер игнорирует, что лишает атакующего возможности раздувать память служебными метаданными частей.
2. **Проверка `post_max_size`:**
   В функции `fill_buffer` добавлено жесткое отсечение при превышении `SG(post_max_size)`.
3. **Безопасная обработка нехватки памяти (OOM exit):**
   Вместо краха ядра парсер проверяет `ZEND_HAS_OOM()`:
   ```c
   if (ZEND_HAS_OOM()) {
       goto oom;
   }
   ...
   oom:
       if (key) {
           efree(key);
       }
       smart_string_free(&buf_value);
       return 0;
   ```
   Парсер возвращает `0` штатно, аккуратно освободив локальные ресурсы.
4. **Обнуление указателя на хэш загруженных файлов:**
   ```c
   zend_hash_destroy(SG(rfc1867_uploaded_files));
   FREE_HASHTABLE(SG(rfc1867_uploaded_files));
   SG(rfc1867_uploaded_files) = NULL;
   ```

### 3.4. Изоляция состояния в CLI Server (`sapi/cli/php_cli_server.c`)

В долгоживущем процессе встроенного сервера при неудачной инициализации запроса теперь принудительно вызывается полный цикл завершения:
```c
/* Run the request shutdown even if the startup failed, so that no
 * request state (e.g. EG(delayed_oom)) leaks into the next request */
php_cli_server_request_shutdown(server, client);
```
Это гарантирует, что флаг `EG(delayed_oom)` от предыдущего запроса не заблокирует обработку последующих соединений.

---

### 3.5. Интеграция с JIT (`ext/opcache/jit/zend_jit_x86.dasc`)

Для архитектуры `x86/x86_64` в код генератора JIT внедрена проверка прерываний виртуальной машины с учётом состояния `delayed_oom`. При взведении прерывания JIT-код своевременно выходит из скомпилированного нативного цикла и передаёт управление диспетчеру VM.
