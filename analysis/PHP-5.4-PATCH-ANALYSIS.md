## 1. Специфика ветки PHP 5.4 и архитектура Zend Engine 2.4

Ветка PHP 5.4 привнесла в PHP трейты (traits), короткий синтаксис массивов `[]` и встроенный веб-сервер, однако подсистема управления памятью и сетевой парсер оставались классическими:
1. **Zend Memory Manager (v2.4):**
   * Память выделяется сегментами с пулами быстрых корзин (`ZEND_MM_CACHE`).
   * В оригинале при превышении лимита `memory_limit` аллокатор немедленно вызывал `zend_error_noreturn(E_ERROR, ...)` и совершал аварийный прыжок `longjmp` (`zend_bailout`). В процессе разбора multipart/form-data это приводило к повреждению структур и освобождению памяти в неопределенном состоянии.
2. **Многопоточный контекст TSRM:**
   * Вся кодовая база опирается на макросы разделяемой памяти потоков `TSRMLS_D`, `TSRMLS_DC`, `TSRMLS_CC`.
3. **Отсутствие безопасного сброса `zend_llist`:**
   * Как и во всех версиях до октября 2026 года, функция `zend_llist_destroy` обнуляла только счетчик элементов `l->count = 0`, оставляя указатели `head` и `tail` указывать на уже освобожденные блоки памяти.

## 3. Детальный аудит ключевых рубежей защиты

### 3.1. Устранение Use-After-Free в связанных списках (`Zend/zend_llist.c`)

В оригинальном `php-5.4.45`:
```c
// До патча:
ZEND_API void zend_llist_destroy(zend_llist *l)
{
    zend_llist_element *current=l->head, *next;
    while (current) {
        next = current->next;
        if (l->dtor) l->dtor(current->data);
        pefree(current, l->persistent);
        current = next;
    }
    l->count = 0; // l->head и l->tail оставались висячими указателями!
}
```

Патч вносит исправление:
```diff
--- a/Zend/zend_llist.c
+++ b/Zend/zend_llist.c
@@ -109,6 +109,8 @@
 		current = next;
 	}
 
+	l->head  = NULL;
+	l->tail  = NULL;
 	l->count = 0;
 }
```
**Эффект безопасности:** Принудительное обнуление указателей `head` и `tail` делает невозможным выполнение повторной очистки или обращение к освобожденным узлам связанного списка при аварийном завершении работы движка.

### 3.2. Архитектура Soft-OOM и Hard Limit (`Zend/zend_alloc.c` и `zend_alloc.h`)

1. **Динамический расчет Hard Limit (`zend_mm_update_hard_limit`):**
   ```c
   size_t headroom = MIN(heap->limit, (size_t) 1024 * 1024 * 1024);
   size_t hard_limit = (heap->limit > (size_t) -1 - headroom) ? (size_t) -1 : heap->limit + headroom;
   heap->hard_limit = hard_limit;
   ```
   Аллокатор выделяет безопасный коридор (headroom) сверх мягкого лимита `memory_limit` (до +100% объема, но не более 1 ГБ).
2. **Мягкое состояние ошибки OOM (`EG(delayed_oom)`):**
   * При достижении значения `limit` выставляется флаг:  
     `EG(delayed_oom) = ZEND_OOM_STATE_PENDING;`
   * Аллокатор **не прерывает** работу и не делает `longjmp`, позволяя парсеру POST-данных штатно обработать отказ.
3. **Безопасная точка аварийной паники (`_exit(137)`):**
   * Если приложение пытается потребить больше жесткого предела (`heap->hard_limit`), срабатывает функция `zend_mm_hard_limit_error`:
     ```c
     fprintf(stderr, "Hard memory limit of %lu bytes exhausted (tried to allocate %lu bytes)...\n", ...);
     _exit(137);
     ```
   * Код завершения `137` (SIGKILL) мгновенно убивает процесс ОС без вызова деструкторов PHP, полностью исключая эксплуатацию состояния гонки или повреждения памяти.

### 3.3. Защита сетевого парсера RFC 1867 (`main/rfc1867.c`)

1. **Строгая фильтрация MIME-заголовков:**
   ```c
   static zend_bool php_mime_should_save_hdr(const char *name)
   {
       return !strcasecmp(name, "Content-Disposition")
           || !strcasecmp(name, "Content-Type");
   }
   ```
   Парсер сохраняет только жизненно необходимые заголовки для разбора файлов. Любые пользовательские или мусорные заголовки отбрасываются до аллокации.
2. **Отсечение по `post_max_size` в буфере:**
   ```c
   if (SG(post_max_size) > 0 && SG(read_post_bytes) > SG(post_max_size)) {
       return 0;
   }
   ```
   Блокирует переполнение буфера входящими сетевыми пакетами.
3. **Безопасный выход по `goto oom`:**
   В случае нехватки памяти парсер очищает выделенные ресурсы и возвращает `0`, не повреждая состояние движка.
