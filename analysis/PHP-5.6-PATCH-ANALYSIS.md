## 1. Архитектурный контекст PHP 5.6 (Zend Engine 2)

PHP 5.6.40 кардинально отличается от линейки PHP 7.x/8.x внутренним устройством ядра:
1. **Аллокатор памяти (Zend Memory Manager v2):**
   * В PHP 5.6 используется сегментный аллокатор с кэшированием корзин (`free_buckets`, `large_free_buckets`, `rest_buckets`), существенно отличающийся от компактного страничного аллокатора PHP 7+.
   * В оригинальном PHP 5.6 исчерпание `memory_limit` вызывало жесткий немедленный `zend_error(E_ERROR, ...)` с последующим длинным прыжком `longjmp` (`zend_bailout`), прерывавшим выполнение на произвольной C-инструкции.
2. **Многопоточный контекст TSRMLS:**
   * В ядре 5.6 все вызовы оперируют макросами `TSRMLS_D` / `TSRMLS_DC` / `TSRMLS_CC` (Thread Safe Resource Manager).
3. **Объем патча:**
   * Патч для 5.6 значительно компактнее версий 7.x (19 файлов против 85+), поскольку фокусируется непосредственно на ядре аллокатора, точке входа парсера POST (`rfc1867.c`), сериализаторе и связном списке `zend_llist`.

## 3. Детальный аудит компонентов защиты в PHP 5.6

### 3.1. Устранение Use-After-Free в связанных списках (`Zend/zend_llist.c`)

В оригинальном `php-5.6.40`:
```c
// До патча:
ZEND_API void zend_llist_destroy(zend_llist *l)
{
    zend_llist_element *current=l->head, *next;
    while (current) {
        next = current->next;
        if (l->dtor) l->dtor(current->data);
        pefree(current, l->persistent);
        current = next;
    }
    l->count = 0; // l->head и l->tail оставались висячими указателями!
}
```

Патч вносит исправление:
```diff
--- a/Zend/zend_llist.c
+++ b/Zend/zend_llist.c
@@ -109,6 +109,8 @@
 		current = next;
 	}
 
+	l->head  = NULL;
+	l->tail  = NULL;
 	l->count = 0;
 }
```
**Эффект безопасности:** Полностью исключает возможность повреждения кучи при вызове деструкторов списков во время аварийного завершения запроса.

### 3.2. Архитектура Soft-OOM и Hard Limit в аллокаторе Zend MM v2 (`Zend/zend_alloc.c`)

В аллокатор Zend Engine 2 внедрена оригинальная адаптация архитектуры Арно Ле Блана:
1. **Вычисление Hard Limit (`zend_mm_update_hard_limit`):**
   * Вычисляется безопасная подушка (headroom):  
     `size_t headroom = MIN(heap->limit, (size_t) 1024 * 1024 * 1024);`  
     `heap->hard_limit = heap->limit + headroom;`
   * Это дает дополнительный буфер памяти сверх `memory_limit`, позволяющий парсеру штатно завершить разбор данных.
2. **Отложенное состояние ошибки (Soft-OOM):**
   * При превышении `limit` взводится статус:  
     `EG(delayed_oom) = ZEND_OOM_STATE_PENDING;`
   * Память продолжает выделяться в пределах `hard_limit`.
3. **Защита от жесткого исчерпания памяти (`zend_mm_hard_limit_error`):**
   * Если запрос превышает жесткий лимит (`add_size > heap->hard_limit`), аллокатор аварийно останавливает процесс:
     ```c
     fprintf(stderr, "Hard memory limit of %lu bytes exhausted (tried to allocate %lu bytes)...\n", ...);
     _exit(137);
     ```
   * Код завершения `137` (SIGKILL 128 + 9) мгновенно убивает процесс ОС, полностью предотвращая выполнение PHP-деструкторов и эксплуатацию уязвимости через манипуляцию памятью.

---

### 3.3. Защита сетевого парсера RFC 1867 (`main/rfc1867.c`)

1. **Строгая фильтрация MIME-заголовков:**
   ```c
   static zend_bool php_mime_should_save_hdr(const char *name)
   {
       return !strcasecmp(name, "Content-Disposition")
           || !strcasecmp(name, "Content-Type");
   }
   ```
   Все сторонние заголовки парсер не сохраняет в память.
2. **Контроль `post_max_size` в буфере ввода:**
   Прямое отсечение в `fill_buffer`:
   ```c
   if (SG(post_max_size) > 0 && SG(read_post_bytes) > SG(post_max_size)) {
       return 0;
   }
   ```
3. **Безопасная точка выхода по Soft-OOM (`goto oom`):**
   При фиксации мягкого OOM парсер освобождает строковые буферы и ключ, не вызывая паники аллокатора.
